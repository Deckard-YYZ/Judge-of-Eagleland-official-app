# 配置系统架构

核对日期：2026-10-15。本文维护制作、生成、运行时消费和版本管理边界。产品行为以 [产品需求](../product/requirements.md) 为依据；当前入口、实施状态及待决事项统一见 [文档索引](../README.md)。

## 与需求文档的分工

需求文档定义哪些内容可以配置、玩家如何交互，以及阶段由哪些游戏事实决定。配置表如何组织、引用如何建立、何时计算条件、怎样保存派发结果，属于本文的架构设计。

产品已明确案件与聊天是平行业务：案件是常态核心，聊天是按剧情需要出现的支线，二者可以同时进行。更高层的主剧情图根据案件判决、聊天最终结果及已有状态条件决定主剧情节点，并开放案件池的一部分、派发特定案件或启动后续聊天。阶段归入这套主控，不另立平行推进系统；此前 1–3 个大阶段的规模预期不限制主剧情节点数量。

## 配置组织与内容制作

按案件与决策、交互与提示、案件池与派发、主剧情与阶段、聊天事件、文案与资源组织逻辑配置，通过稳定 ID 引用关联内容。逻辑分类不直接等于最终文件或表格数量。

采用统一的内容规范：配置编辑来源经过校验与生成，形成运行时读取的版本内容包。每类内容保留明确的权威编辑来源，避免表格与生成后的 JSON 同时人工维护。

作者以表格为主要编辑入口。案件清单、选项、数值、条件引用、触发绑定和池成员由表格管理；长文、多语言文案及复杂分支由独立结构化文本管理，通过稳定 ID 关联。同一字段只有一个权威编辑来源，生成文件不接受人工修改。

配置校验应定位无效字段、缺失引用及内容完整性问题，并支持解释某项内容为何触发、派发或未满足条件。已有玩法能力内新增同类内容，应能通过配置完成。

## 生成工具与运行时边界

Luban 承担表格读取、作者数据类型、基础约束校验和中间数据生成；TypeScript 构建工具将生成结果与文案、分支文件汇合，生成项目现有加载边界能够读取的版本内容包。

```text
表格与结构化文本
        ↓
Luban 导表及基础校验
        ↓
TypeScript 内容组装与游戏专属校验
        ↓
版本内容包与来源诊断
        ↓
ContentRepository → Application / Game Core → UI
```

Luban 和 .NET 只进入作者及构建环境，不进入游戏运行时。浏览器与 Tauri 均消费生成后的数据；不在玩家端读取 Excel，也不为配置另建数据库或联网服务。

Luban 工具版本必须固定，记录来源及版本或提交。开发者通过环境变量或命令参数指定本地工具位置，不把本机绝对路径提交为项目默认配置。仓库应包含配置定义、作者样本、生成命令及生成结果验证方式。

运行时内容结构继续由项目 Zod Schema 定义，TS 类型从 Schema 推导。Luban 的作者模型只描述表格字段；组装层明确把作者模型转换为运行时模型，并在输出处执行运行时校验。不得另外手写一套与运行时完全重复的 TS 接口。若后续改为由工具统一生成 Schema，必须整体迁移结构权威来源，不能双向人工同步。

条件和效果使用有限的类型集合，禁止把任意 JavaScript、表达式求值或无约束 JSON 字符串作为通用规则入口。长文及复杂分支虽以文本编辑，仍须有结构、引用和业务校验。

## 配置分组与消费接口

逻辑分组如下。物理表格可按可读性拆分；消费者通过内容契约和查询接口读取，不依赖工作簿名、工作表顺序或原始单元格。

| 分组         | 配置责任                                             | 消费边界                           |
| ------------ | ---------------------------------------------------- | ---------------------------------- |
| 案件与决策   | 案件、选项组、选项目标、判决及状态效果               | Game Core 的案件推进               |
| 交互与提示   | 指示框目标及展示参数、ActionInput 内容及业务触发标记 | 业务事件查询与交互呈现             |
| 条件与资格   | 案件判决、属性、标记、主剧情位置和聊天最终结果条件   | 同步、无副作用的条件计算           |
| 案件池与派发 | 候选成员、资格条件、时机、显式选取策略               | 候选查询与派发计划                 |
| 主剧情与阶段 | 主剧情节点、转移条件、阶段归属及内容开放或启动意图   | 读取业务事实的主控查询及其提交消费 |
| 聊天事件     | 局部剧情树、回复、终止节点与结果、无交互关闭配置     | 聊天局部推进与最终结果出口         |
| 文案与资源   | 本地化文本、资源 ID 与安全路径                       | 已有本地化和资源加载边界           |

配置系统提供可读取、可校验、可解释的定义和运行时消费契约。导表、Core/Session 接入和 UI 呈现分别验证；当前接入状态统一见 [文档索引](../README.md)。

## 主剧情图与业务结果

主剧情图维护游戏整体推进的位置；案件和聊天各自维护局部进度。主控条件读取案件判决、已经结束的聊天事件结果及已有状态，不读取进行中聊天的内部节点。聊天的终止节点可以作为结果标识或映射到配置结果，主控所见的都是该次聊天已结束的事实。

主剧情节点配置条件与后续意图：开放哪些案件池范围、派发哪个特定案件、启动哪个聊天事件，以及进入哪个后继主剧情节点。阶段是主剧情的组织信息或位置，统一由主控推进，不作为与案件、聊天平行运行的业务，也不独立维护另一套阶段转移系统。

使用游戏专属、有限的条件与意图类型表达这张图，复用现有同步纯 Core 计算。条件组合、引用关系与结果映射应在配置契约中明确，图结构不预设为线性，也不受此前大阶段数量预期限制。规则冲突及派发策略仍保留待决边界。

## 聊天事件与主控接口

一次聊天事件是“被动弹出 → 局部剧情树交互 → 被动关闭”的最小完整内容。局部节点只由聊天交互推进；玩家选择回复后，发送该选项文本并进入配置的预制回复分支。达到终止节点时，事件被动关闭，产生一次配置的最终结果交给主控。内部节点不直接解锁案件、启动其他聊天或切换主剧情节点，这些后续行为由主控根据最终结果决定。

通常同时出现一个聊天事件，特殊剧情可以配置多个；不在工程中设为只能有一个。玩家没有主动打开、收起或关闭聊天框的操作，可以搁置当前聊天继续判案。各聊天事件分别保存自己的状态、局部位置和无交互计数；对一个聊天的回复只重置该聊天的计数。

无交互关闭是否启用、阈值及关闭后的最终结果均由配置确定，不设全局默认次数。计数依据聊天未获回复期间已成功推进案件的选项选择次数，不按现实时间、打开应用时长或离线时间计算；达到该聊天的配置阈值时，被动结束该事件并产生配置结果。案件选择不会推进聊天内部节点或替玩家发送回复，只参与这项关闭判定。

“成功推进”以案件选择提交成功为准。一次选择如何在候选状态中计数、是否形成关闭结果以及何时让主控消费，属于工程提交边界，应共同形成一次可保存的转换结果，不能在保存失败后仍累计计数或发布关闭效果。并发聊天的计数及关闭判断分别进行，不共享一个全局无交互计数。

退出登录保存进行中的聊天事件及其计数，重新登录恢复已有位置和呈现；离线时间不推进聊天。保存同时包含已结束事件的最终结果、主剧情位置和已经消费的推进或派发事实，使恢复后不会重复启动聊天、重复消费结果或重新派发。

聊天查询提供局部节点与回复选项、回复后的候选状态、无交互关闭后的候选状态及最终结果；主控查询只消费终局结果和其他业务事实，返回主剧情后继及内容开放或派发意图。Application 在同一次 CAS 成功保存后发布这些状态与呈现变化，沿用现有“计算候选状态 → 条件保存 → 发布快照”边界。现行字段与执行次序见 [主流程运行时契约](main-flow.md)。

## 旧 schema 5 的兼容边界

[配置系统实施记录](../archive/implementation/configuration.md) 已验收作者链路、内容校验和旧流程纯查询；其中 `chatLastNode`、进行中聊天节点、`externalBranches` 及聊天节点直接返回解锁或阶段意图，是此前验证模型的能力，不是新玩法契约。不能把任意历史或进行中节点接入主控条件，也不能沿用案件事件推进聊天内部隐藏分支、聊天节点直接解锁内容的行为。

schema 6 通过主剧情图、聊天最终结果、无交互计数、保存恢复与一次 CAS 后发布执行新流程。旧 schema 5 的公开 flow 查询不自动写入 Session 或存档，不能混用两者。运行时字段与执行契约见 [主流程运行时契约](main-flow.md)。

## 案件资格与实际派发

区分候选资格、派发时机和选取策略：满足状态条件的案件可以进入可用范围，但是否立即发给玩家、发出哪一个，仍由派发规则决定。

固定顺序、优先级和随机选取属于不同策略，“从池中选取”本身不确定采用哪一种。若使用随机，实际选中结果应与本次推进事实一起保存，恢复时不重新抽取。

继续保持配置与玩家事实分离。内容包定义案件、条件、效果和文案；存档记录实际派发结果及推进状态。主剧情变更与相应开放、派发或聊天启动事实应在同一次保存中提交。

未明确多条规则冲突、空候选池等业务策略时，纯查询可以返回候选、原因及需要决策的结果；不能擅自取第一条、随机选取、静默结束游戏或默认派发全部。小样可以明确指定一个验证策略，该策略只作用于对应样本配置。

## 校验与兼容

生成分为结构校验、引用及图校验、项目语义校验和内容包读取验证。错误至少提供源文件、对象 ID 和字段位置；表格来源尽可能保留工作表、行和列信息。生成失败不得留下可被误认为成功的新内容包，也不得破坏已有有效输出。

同一份输入应产生稳定输出；校验模式应能检测作者来源与提交产物不一致。已发布的 `packageId + version` 继续作为精确版本边界，旧包和旧存档绑定不被样本更新覆盖。新增不兼容字段通过新的内容 Schema 版本表达；旧版本保留原有读取语义。

沿用 Game Core 的同步纯转换与 Application 的“计算候选状态 → 条件保存 → 发布快照”边界。生成工具不进入这条运行路径。错误处理、来源诊断和规则解释不得绕过存档提交或提前发布效果。

校验通过只证明配置结构及已检查规则有效，不证明剧情合理、数值平衡或尚未实现的 UI 行为符合产品需求。
